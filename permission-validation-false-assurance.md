# Security advisory: a negative permission check could report false assurance

**Written:** October 8, 2026. The underlying issue was recorded and corrected in source on August 26, 2026.

**Author:** Richard Wilken, with AI-assisted research and implementation credit. The original internal finding was raised by a Codex Sol review and reviewed separately within the project. A directed AI agent implemented the correction; the fix is committed under Richard’s Git identity and includes an AI coauthor. Discovery and implementation credit are shared as described; no CVE is claimed.

A private read-only NetSuite connector includes a validation step intended to show that a restricted role cannot query a record type outside its permitted scope. In the source-declared 0.1.0 version, the validator treated **any** error from that negative query as proof that the role denied access. A temporary service error or a SELECT rejected by the server for its query shape could therefore produce a successful validation result even though the role’s restriction had not been established.

The operator must already have configured credentials and run the check. Token acquisition and a separate positive query must succeed first. If the negative query returns data, the old code correctly fails validation. The defect occurs when that negative query fails for a reason other than permission denial. An internal offline injected-response check recorded a successful token and positive query followed by a transient server error; the old validator reported the negative check as successful. The historical check is not evidence of a live unauthorized read.

The practical risk is **false assurance during role setup**. If the role is also accidentally too broad, an unrelated negative-query error could conceal that configuration mistake before the credential is used. The connector itself does not grant NetSuite permissions, and the reviewed record establishes no attacker control of the error, credential theft, bypass of NetSuite authorization, or access to protected data.

The source-declared 0.1.1 correction retains the response status, error code, and detail. It accepts a negative result only when its predicate recognizes a denial shape: HTTP 403, an allowlisted permission error code, or permission wording in the server detail after quoted caller input is removed. Responses without a recognized denial signal are reported as inconclusive and return failure. Historical offline regression cases include a response representing permission denial, invalid query, rate limit, server error, exhausted authentication retry, and returned rows. A permission-worded detail still needs interpretation in its actual context; these tests do not prove every possible service response is classified correctly.

The introducing and correcting source revisions have been inspected, but their version strings are not verified public release identifiers. The records do not establish which packaged copy, if any, was distributed or deployed, nor that a corrected package replaced it. No new tests or external requests were made in preparing this advisory. Claims about distributed or deployed packages would require separate package and release evidence.
